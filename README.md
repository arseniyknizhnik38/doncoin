# DONCOIN

> START AS NOBODY. BECOME THE DON.

Full-stack монорепозиторий на npm workspaces:

| Пакет    | Стек                                       | Dev-порт |
| -------- | ------------------------------------------ | -------- |
| `client` | React 19 + TypeScript + Vite + Tailwind v4 | `5173`   |
| `server` | Node.js + Express 5 + TypeScript (tsx)     | `3000`   |

## Требования

- Node.js >= 20 (проверено на 24)
- npm >= 10

## Установка

```bash
npm install
```

Одна команда в корне ставит зависимости обоих воркспейсов.

## Запуск в режиме разработки

```bash
npm run dev
```

Через `concurrently` поднимаются одновременно:

- API — http://localhost:3000 (автоперезагрузка через `tsx watch`)
- UI — http://localhost:5173 (Vite HMR)

Vite проксирует `/api/*` на сервер, поэтому из фронтенда можно ходить на
относительные пути (`fetch('/api/health')`) без CORS-настроек.

Запустить что-то одно:

```bash
npm run dev:server
```

```bash
npm run dev:client
```

## Сборка

```bash
npm run build
```

- `server` → `server/dist` (компиляция `tsc`)
- `client` → `client/dist` (статика Vite)

Запуск собранного API:

```bash
npm start
```

## Переменные окружения

Скопируйте `server/.env.example` в `server/.env` и задайте `PORT` при

## База данных (PostgreSQL + Prisma 7)

Схема: [`server/prisma/schema.prisma`](server/prisma/schema.prisma) — модель `User`
(`id`, `telegramId` unique, `username?`, `firstName?`, `createdAt`, `updatedAt`).

### 1. Строка подключения

Откройте `server/.env` и замените значение в кавычках на строку из Neon
(Dashboard → проект → **Connect** → Connection string):

```
DATABASE_URL="postgresql://USER:PASSWORD@HOST.neon.tech/DBNAME?sslmode=verify-full"
```

Файл `server/.env` исключён из git. Шаблон без секретов — `server/.env.example`.

> В Prisma 7 `.env` не читается автоматически: его загружает
> `server/prisma.config.ts` (`import "dotenv/config"`), оттуда же CLI берёт
> `datasource.url`. Рантайм-сервер грузит `.env` в `server/src/index.ts`.

### 2. Применить схему к базе

```bash
npm run db:migrate
```

Создаст SQL-миграцию в `server/prisma/migrations/`, применит её к базе и
перегенерирует Prisma Client. Миграции коммитятся в git.

Быстрая альтернатива для прототипа, без файлов миграций:

```bash
npm run db:push -w server
```

На проде/CI применение уже созданных миграций:

```bash
npm run db:deploy -w server
```

### 3. Прочее

Перегенерировать клиент (запускается автоматически в `dev` и `build`):

```bash
npm run db:generate
```

Просмотр данных в браузере:

```bash
npm run db:studio
```

### Использование клиента в коде

Клиент — синглтон в [`server/src/lib/prisma.ts`](server/src/lib/prisma.ts)
(Prisma 7 работает через driver adapter `@prisma/adapter-pg`):

```ts
import { prisma } from './lib/prisma.js';

const user = await prisma.user.upsert({
  where: { telegramId },
  update: { username, firstName },
  create: { telegramId, username, firstName },
});
```

Сгенерированный клиент лежит в `server/src/generated/prisma/` и в git не
попадает — после `git clone` выполните `npm install && npm run db:generate`.

## Telegram Mini App

Пакет: [`@telegram-apps/sdk-react`](https://docs.telegram-mini-apps.com/) 3.3.9 —
официальный React-биндинг платформы Telegram Mini Apps.

Инициализация — [`client/src/telegram/init.ts`](client/src/telegram/init.ts),
вызывается в `main.tsx` до рендера React:

| Что делает                                   | Метод SDK                                        |
| -------------------------------------------- | ------------------------------------------------ |
| Разворачивает окно на весь экран              | `viewport.expand()`                              |
| Красит фон, шапку и нижнюю панель в `#0A0A0A` | `miniApp.setBackgroundColor/HeaderColor/BottomBarColor` |
| Отдаёт реальную высоту окна в CSS             | `viewport.bindCssVars()` → `--tg-viewport-*`     |
| Сообщает клиенту о готовности UI              | `miniApp.ready()`                                |
| Данные пользователя                           | `initData.restore()` → сигнал `initData.user`    |

Вне Telegram `isTMA()` возвращает false, SDK не инициализируется, страница
показывает «Тестовый режим (не в Telegram)». Ошибки SDK перехватываются —
приложение деградирует до браузерного режима, а не падает белым экраном.

Имя пользователя берётся хуком
[`useTelegram()`](client/src/telegram/useTelegram.ts).

### Быстрая проверка без Telegram (мок)

```bash
npm run dev:mock
```

Подставляет фиктивное окружение Telegram (`mockTelegramEnv`), страница
показывает тестового пользователя «Vito Corleone», а в консоли видны команды,

Мок не проверяет подпись initData — для этого нужен запуск в настоящем Telegram.

### Как протестировать внутри настоящего Telegram

Telegram открывает Mini App только по **публичному HTTPS-адресу**, поэтому
`localhost` напрямую не подойдёт — нужен туннель.

**1. Поднять приложение локально**

```bash
npm run dev
```

**2. Пробросить порт 5173 наружу по HTTPS** (в отдельном терминале):

```bash
ssh -R 80:localhost:5173 nokey@localhost.run
```

Команда выведет адрес вида `https://911a9c7077d4fe.lhr.life`. Аккаунт и ключи
не нужны, туннель идёт по ssh (порт 22) и проходит через VPN/прокси.

Другие варианты, если этот недоступен:

| Сервис | Команда | Замечание |
| --- | --- | --- |
| localhost.run | `ssh -R 80:localhost:5173 nokey@localhost.run` | без регистрации, без заглушек |
| pinggy | `ssh -p 443 -R0:localhost:5173 a.pinggy.io` | работает через 443, сессия 60 мин |
| cloudflared | `npx cloudflared tunnel --url http://localhost:5173` | нужен **порт 7844** (UDP или TCP) |
| ngrok | `ngrok http 5173` | нужен бесплатный аккаунт + токен |
| localtunnel | `npx localtunnel --port 5173` | **не годится**: показывает браузерам страницу-заглушку, Telegram увидит её вместо приложения |

> **Если включён VPN/прокси в режиме TUN + fake-IP** (все домены резолвятся в
> `198.18.x.x`), cloudflared не поднимется: он ходит на порт 7844, который такие
> прокси обычно не пропускают — в логах будет `QUIC connection failed`, а с
> `--protocol http2` — `TLS handshake with edge error: EOF`. Лечится либо
> отключением прокси, либо ssh-туннелем из таблицы выше.

**3. Хост туннеля уже разрешён.** Vite отвечает 403 Blocked request на чужой
Host-заголовок, поэтому в `client/vite.config.ts` заранее прописан
`server.allowedHosts` для доменов localhost.run, serveo, pinggy, cloudflared,
ngrok и localtunnel. Другой сервис — добавьте его домен в этот список.

Если через туннель не работает HMR, допишите туда же `hmr: { clientPort: 443 }`.

**4. Создать бота и Mini App в [@BotFather](https://t.me/BotFather)**

- `/newbot` → имя и username бота → получите токен (он понадобится позже для
  серверной валидации initData);
- `/newapp` → выбрать бота → название, описание, картинку 640×360 → **Web App
  URL**: вставить HTTPS-адрес туннеля;
- BotFather вернёт ссылку вида `https://t.me/ваш_бот/имя_приложения`.

Быстрее без `/newapp`: `/mybots` → бот → **Bot Settings → Menu Button → Edit
menu button URL** → адрес туннеля. Тогда Mini App открывается кнопкой меню в
чате с ботом.

**5. Открыть ссылку в Telegram** — на телефоне или в Telegram Desktop.
Должно быть видно: приложение развёрнуто на весь экран, фон тёмный (не белый),
на карточке — ваше настоящее имя из Telegram.

### Отладка внутри Telegram

- **Telegram Desktop:** Настройки → Продвинутые → Экспериментальные настройки →
  включить **Enable webview inspecting**, затем правый клик по Mini App →
  «Inspect».
- **Android:** включить отладку по USB и открыть `chrome://inspect` на
  компьютере.
- **iOS:** Safari → Разработка → устройство (нужен Web Inspector в настройках
  Safari на телефоне).

Если в Telegram страница пустая — почти всегда это одно из трёх: адрес не
HTTPS, домен туннеля не добавлен в `allowedHosts` (тогда туннель отдаёт 403
Blocked request), либо сервис туннеля показывает свою страницу-заглушку.

## Авторизация через Telegram

### Как это работает

1. Клиент внутри Telegram получает от SDK сырую строку `initData` (сигнал
   `initDataRaw`) и отправляет её в `POST /api/auth/telegram`
   — [client/src/telegram/useAuth.ts](client/src/telegram/useAuth.ts).
2. Сервер проверяет подпись по алгоритму Telegram
   — [server/src/lib/telegram.ts](server/src/lib/telegram.ts):

   ```
   secret_key       = HMAC_SHA256(key = "WebAppData", message = TELEGRAM_BOT_TOKEN)
   data_check_string= поля initData кроме hash и signature, отсортированы, склеены через 

   ожидаемый hash   = HMAC_SHA256(key = secret_key, message = data_check_string)
   ```

   Сравнение — `timingSafeEqual`. Дополнительно отвергаются данные старше
   24 часов (`auth_date`).
3. Если подпись верна — пользователь ищется по `telegramId`; если его нет,
   создаётся новый — [server/src/routes/auth.ts](server/src/routes/auth.ts).

Ответ:

```json
{
  "isNew": true,
  "user": {
    "id": "f1ac2ccd-...",
    "telegramId": "999000001",
    "username": "test_don",
    "firstName": "Тест",
    "referredByCode": "REF123",
    "createdAt": "2026-08-24T11:33:32.867Z"
  }
}
```

Коды ошибок: `400` — нет поля `initData`; `401` — подпись не сошлась или
данные протухли; `503` — на сервере не задан `TELEGRAM_BOT_TOKEN`.

При повторных открытиях обновляются `username` и `firstName`, а
`referredByCode` не перезаписывается — кто пригласил, тот и остаётся.

### Реферальные ссылки

Telegram кладёт в `start_param` то, что указано в ссылке на Mini App:

```
https://t.me/ваш_бот/имя_приложения?startapp=КОД
```

Значение сохраняется в поле `referredByCode` при создании пользователя.
Начисление наград — отдельная задача.

### Как получить и вставить токен бота

1. Откройте [@BotFather](https://t.me/BotFather) → `/mybots` → выберите бота →
   **API Token**. (Для нового бота: `/newbot` → токен приходит сразу.)
   Токен выглядит как `8123456789:AAH...` — это пароль от бота, его нельзя
   публиковать и коммитить.
2. Вставьте его в `server/.env`, в кавычки:

   ```
   TELEGRAM_BOT_TOKEN="8123456789:AAH..."
   ```

3. Перезапустите `npm run dev` — переменные читаются при старте.
   Если токен не задан, при старте сервера в консоли появится предупреждение.

Токен нужен только серверу. На клиент он не передаётся и в бандл не попадает.

### Как проверить, что пользователь появился в базе

1. Запустите `npm run dev`, поднимите туннель и откройте Mini App в Telegram.
2. На карточке должно появиться «Аккаунт создан» (при первом открытии) или
   «Аккаунт подтверждён» (при повторных).
3. Посмотрите строку в базе:

   ```bash
   npm run db:studio
   ```

   http://localhost:5555 → таблица `User`. Там будут ваш `telegramId`,
   `username`, `firstName` и `referredByCode` (если заходили по ссылке с
   `?startapp=КОД`).

Проверить реферальную ссылку: откройте
`https://t.me/ваш_бот/имя_приложения?startapp=TEST123` — у нового пользователя
в `referredByCode` окажется `TEST123`.

> Локально всё это можно погонять без Telegram: `npm run dev:mock` — см.
> раздел «Игровая механика».

## Тесты

```bash
npm test
```

Покрыта экономика — то место, где ошибка не роняет сборку, но ломает
прогресс всем игрокам сразу: пороги рангов, кривые улучшений, ежедневный
бонус, оффлайн-доход, задания дня, каталог бизнесов и рекламные кампании.

Проверяются не конкретные числа (они меняются при каждом ребалансе), а
свойства, ломаться которым нельзя: пороги идут по возрастанию, цена уровня
всегда выше предыдущей, окупаемость бизнеса растёт вместе с ценой, задания
дня не повторяются, кампания не выдаёт больше подписок, чем оплачено.

Тесты уже приносили пользу: проверка роста ежедневного бонуса вскрыла, что
после тройной награды седьмого дня восьмой платит втрое меньше. Механика
оказалась верной, а посылка теста — нет, и это ровно тот разговор, ради
которого тесты и пишут.

Отдельно живёт [симуляция прогресса](server/scripts/simulate-progress.ts) —
не тест, а отчёт: прогоняет игрока по реальному конфигу и печатает, на какой
день он берёт каждую ступень. Запускается в CI, чтобы сдвиг баланса был
виден в логе.

```bash
cd server && npx tsx scripts/simulate-progress.ts
```

## Деплой на Vercel

Клиент и API живут на одном домене: статика собирается из `client/dist`, а весь
`/api/*` обслуживает одна serverless-функция [api/index.ts](api/index.ts),
которая переиспользует то же Express-приложение, что и локальный сервер
([server/src/app.ts](server/src/app.ts)). Правила сборки — в
[vercel.json](vercel.json).

Благодаря общему домену фронтенду не нужен отдельный адрес API и не нужен CORS,
а в BotFather адрес прописывается один раз.

### Первый деплой

**1. Создайте пустой репозиторий на GitHub** (без README и .gitignore) и
подключите его:

```bash
git remote add origin https://github.com/ВАШ_ЛОГИН/doncoin.git
```

```bash
git push -u origin main
```

**2. Импортируйте проект в Vercel:** [vercel.com/new](https://vercel.com/new) →
войти через GitHub → **Import** напротив репозитория.

Настройки сборки Vercel возьмёт из `vercel.json`, менять их не нужно
(Framework Preset — `Other`).

**3. Добавьте переменные окружения** в том же экране импорта
(**Environment Variables**) или потом в **Settings → Environment Variables**:

| Переменная | Значение |
| --- | --- |
| `DATABASE_URL` | строка подключения Neon — возьмите вариант **с пулингом** (в хосте есть `-pooler`) |
| `TELEGRAM_BOT_TOKEN` | токен бота из @BotFather |

Пулинг важен: serverless-функции создают много коротких подключений, и без
пулера база быстро упрётся в лимит соединений.

**4. Нажмите Deploy.** Через пару минут получите адрес вида
`https://doncoin.vercel.app`.

**5. Пропишите этот адрес в BotFather** — `/mybots` → бот →
**Bot Settings → Menu Button → Edit menu button URL**. Больше менять его не
придётся: адрес постоянный.

### Проверка после деплоя

```bash
curl https://ВАШ_ПРОЕКТ.vercel.app/api/health
```

Должно вернуться `{"status":"ok"}`. Затем откройте Mini App в Telegram —
на карточке появится «Аккаунт создан» или «Аккаунт подтверждён».

Логи функции: Vercel → проект → **Logs** (там же видны ошибки Prisma и 401 от
проверки подписи).

### Обновления

Каждый `git push` в `main` автоматически пересобирает прод. Ветки и pull
request'ы получают отдельные превью-адреса — их удобно скармливать BotFather
во втором тестовом боте.

### Миграции базы

Миграции и каталог накатываются самой сборкой: `vercel-build` — это
`db:deploy && db:seed && db:generate && build`. То есть `git push` обновляет
и код, и схему, и содержимое каталогов одним движением, а рассинхрона между
кодом и базой не бывает по построению.

Оба шага идемпотентны: `migrate deploy` применяет только непринятые миграции,
а сид обновляет записи по `slug`, а не плодит дубли.

**Требование:** в Vercel переменная `DATABASE_URL` должна быть доступна на
этапе **Build**, а не только Runtime (Project → Settings → Environment
Variables → галочка Build). Иначе сборка упадёт на первом же шаге — это
намеренно: лучше не выкатить релиз, чем выкатить код на старую схему.

Новые миграции по-прежнему **создаются** локально, на дев-базе:

```bash
npm run db:migrate
```

Она пишет SQL-файл в `server/prisma/migrations/`, его и коммитим. На проде
файл применит уже сборка.

### Локальная разработка после деплоя

Ничего не меняется: `npm run dev` поднимает Express на `:3000` и Vite на
`:5173` с прокси `/api`. Туннель нужен, только если хотите отлаживать
незадеплоенные правки прямо в Telegram.

## Игровая механика: баланс и тапы

### Экономика

| Параметр | Поле в базе | Стартовое значение |
| --- | --- | --- |
| Баланс | `balance` (BigInt) | 0 |
| Обойма | `energy` / `energyMax` | 6000 / 6000 (= 600 тапов) |
| Восстановление | `energyPerSecond` | 1 в секунду (= 6 тапов в минуту) |
| Награда за тап | `coinsPerTap` | 10 |

Стартовые значения берутся из нулевых уровней каталога (`START_STATE` в
[lib/upgrades.ts](server/src/lib/upgrades.ts)), а не из `@default` схемы:
иначе правка баланса требовала бы миграции.

**Энергия хранится в долях тапа.** Один тап стоит `ENERGY_PER_TAP` = 10
единиц ([lib/energy.ts](server/src/lib/energy.ts)). Это единственный способ
задать медленный реген целым числом: обойма в 600 тапов копится 100 минут,
тогда как «1 тап в секунду» наполняла бы её за 10 минут — и возвращаться в
игру было бы незачем. Игроку числа показываются в тапах.

### Эндпоинты

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/game/state` | баланс и энергия с учётом восстановления |
| `POST` | `/api/game/tap` | начислить монеты, тело `{ "taps": 1..50 }` |

Оба требуют заголовок с теми же initData, что и вход:

```
Authorization: tma <raw initData>
```

Подпись проверяется на каждом запросе — сервер не доверяет клиенту даже
telegramId.

### Почему накрутить нельзя

- клиент присылает только **количество тапов**, награду считает сервер по
  `coinsPerTap` из базы;
- больше энергии, чем есть, потратить нельзя — лишние тапы просто не
  засчитываются (`accepted` в ответе меньше запрошенного);
- за один запрос принимается не больше 50 тапов;
- энергия и баланс меняются одним атомарным `UPDATE ... RETURNING`
  ([server/src/lib/game.ts](server/src/lib/game.ts)), поэтому параллельные
  запросы не могут списать одну и ту же энергию дважды;
- время берётся из `now()` базы, а не из часов клиента или сервера.

### Как это ощущается на клиенте

Тап засчитывается локально мгновенно, а на сервер уходит пачкой раз в 700 мс
([client/src/game/useGame.ts](client/src/game/useGame.ts)). Ответ сервера
перезаписывает состояние — он источник правды. Поэтому задержка до базы не
мешает играть, а расхождения самоисправляются.

Отказы `401` (сессия истекла) и `429` (лимит частоты) означают, что запрос
даже не дошёл до начисления, поэтому такие тапы возвращаются в очередь и
уходят повторно — счёт на экране не разъезжается с базой. Сетевые ошибки не
переигрываются: запрос мог дойти, и повтор списал бы энергию дважды.

Данные вкладок «Дело», «Клан» и «Топ» перезапрашиваются при открытии вкладки,
а доступность покупки считается от текущего баланса, а не от снимка каталога.

### Локальная разработка игры без Telegram

```bash
npm run dev:mock
```

Поднимает клиент с фиктивным окружением Telegram и сервер с фиктивным токеном
(`123456:TEST_ONLY_NOT_A_REAL_TOKEN`). Мок подписывает initData тем же
токеном, поэтому проверка подписи проходит и игровой цикл работает целиком —
включая запись в базу.

Токен-заглушка задан в `client/.env.mock` и в скрипте `dev:mock` сервера;
настоящий токен из `server/.env` при этом не используется. В прод-сборку код
мока не попадает.

## Реферальная система

### Как устроено

У каждого игрока есть свой код (`referralCode`, 8 символов без похожих 0/O/1/I)
и ссылка вида:

```
https://t.me/ИМЯ_БОТА/ИМЯ_ПРИЛОЖЕНИЯ?startapp=КОД
```

Telegram кладёт код в `start_param` внутри initData. При **первой** регистрации
сервер находит владельца кода и запоминает связь.

| Кому | Сколько | Когда |
| --- | --- | --- |
| Новичку | 10 000 | сразу, при регистрации |
| Пригласившему | 25 000 | когда новичок сделает 2 000 тапов |

### Почему пригласившему платят не сразу

Раньше платили в момент регистрации — то есть монеты чеканились скриптом:
заведи аккаунт, открой приложение по чужой ссылке, повтори. Для игры, которая
зарабатывает на рекламе, это не просто инфляция: рекламодатель платит за
подписчиков, а накрученные аккаунты выжигают оплаченные места и не приносят
ему ничего. Заодно реферальный топ показывал не тех, кто привёл живых людей,
а тех, у кого больше аккаунтов.

Порог задан в тапах, а не в заработке: заработок набирается заданиями и
бонусами почти мгновенно, а тапы упираются в энергию — две тысячи это четыре
полные обоймы, то есть несколько заходов и часы восстановления. Накрутка
остаётся возможной, но перестаёт быть бесплатной.

Отметка о выплате ставится условием в `UPDATE` (`referralRewarded`), поэтому
две одновременные пачки тапов не заплатят дважды. Проверка идёт после каждой
пачки, но до базы доходит ровно один раз за всю жизнь игрока: пока порог не
взят или награда уже выдана, функция выходит без единого запроса.

Связь «кто кого привёл» не переписывается, код нормализуется (регистр не
важен), несуществующий код игнорируется.

Эндпоинт: `GET /api/referrals` — свой код, число приглашённых, сколько из них
засчитано, заработок и список друзей с прогрессом каждого
([server/src/routes/referrals.ts](server/src/routes/referrals.ts)).

### Что нужно настроить, чтобы ссылки заработали

Кнопка меню в чате **не передаёт** `startapp`, поэтому нужен прямой адрес
Mini App:

1. В [@BotFather](https://t.me/BotFather): `/newapp` → выбрать бота → название,
   описание, картинка 640×360 → **Web App URL**: `https://doncoin.vercel.app`.
   BotFather выдаст ссылку `https://t.me/ВАШ_БОТ/ИМЯ_ПРИЛОЖЕНИЯ`.
2. В Vercel → проект → **Settings → Environment Variables** добавить:

   | Name | Value |
   | --- | --- |
   | `VITE_MINI_APP_LINK` | `https://t.me/ВАШ_БОТ/ИМЯ_ПРИЛОЖЕНИЯ` |

3. Пересобрать проект (**Deployments → ⋯ → Redeploy**): переменные с префиксом
   `VITE_` попадают в бандл на этапе сборки, поэтому без пересборки ссылка
   останется старой.

Без этой настройки экран «Семья» покажет запасной вариант
`https://t.me/DonCoinTapGameBot?startapp=КОД` — он сработает, только если у
бота настроено главное Mini App.

### Проверка

Откройте свою ссылку с другого аккаунта Telegram: у новичка стартовый баланс
станет 10 000, а у вас на вкладке «Семья» вырастет «Приглашено» и друг

## Магазин улучшений

Три ветки прокачки, у каждой 20 уровней. Цена удваивается с каждым уровнем.

| Улучшение | Что даёт | Стартовая цена |
| --- | --- | --- |
| **Хватка** | +1 монета за тап за уровень | 500 |
| **Выносливость** | +2 000 к запасу энергии | 500 |
| **Связи** | +1 энергии в секунду | 800 |

Цена растёт в 1.6 раза за уровень. Изначально было ×2, но польза от уровня
растёт линейно, а цена экспоненциально — окупаемость удваивалась с каждой
покупкой, и примерно с восьмого уровня апгрейд терял смысл.

Формулы и цены — в одном месте:
[server/src/lib/upgrades.ts](server/src/lib/upgrades.ts). Уровни хранятся
отдельными полями (`tapLevel`, `energyLevel`, `regenLevel`), а рабочие
параметры (`coinsPerTap`, `energyMax`, `energyPerSecond`) пересчитываются
при покупке — так игровой SQL просто читает готовые значения, а формула не
дублируется в базе.

### Эндпоинты

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/upgrades` | каталог с уровнями, ценами и «хватает ли монет» |
| `POST` | `/api/upgrades/:id/buy` | купить следующий уровень |

Списание атомарное: один `UPDATE` с условиями «денег хватает» и «уровень не
изменился с момента чтения». Поэтому две одновременные покупки не могут ни
увести баланс в минус, ни дать два уровня по цене одного — каждая покупка
оплачивается по своей цене.

Коды ошибок: `409 NOT_ENOUGH_COINS`, `409 MAX_LEVEL`, `409 CONFLICT`
(уровень изменился между чтением и записью — клиенту достаточно повторить).

### На клиенте

Вкладка **Дело** ([client/src/upgrades/ShopScreen.tsx](client/src/upgrades/ShopScreen.tsx)).
Ответ на покупку содержит и новое игровое состояние — оно сразу уезжает в
`useGame`, поэтому на вкладке «Игра» баланс и «+N за тап» обновляются без
перезагрузки.

## Respect

Вторая валюта — медленная и репутационная. Начисляется **только за тапы**:
одна единица за каждые 50 тапов (`TAPS_PER_RESPECT` в
[server/src/lib/game.ts](server/src/lib/game.ts)).

### Почему детерминированно, а не «шанс с каждого тапа»

Тапы приходят на сервер пачками до 50 штук, а не поштучно. Случайный бросок
на пачку дал бы другое распределение, чем бросок на каждый тап, и результат
зависел бы от скорости интернета игрока: при плохой связи пачки крупнее,
бросков меньше. Пришлось бы либо повторять розыгрыш N раз в SQL, либо считать
биномиальное распределение — и то и другое сложнее и хуже проверяется.

Поэтому счётчик: незавершённый остаток хранится в `respectProgress`, целые
единицы уходят в `respect`. Свойства такие:

- 50 тапов дают ровно 1 Respect — одной пачкой, пятью по 10 или пятьюдесятью
  по одному (проверено тестом);
- ничего не теряется при закрытии приложения посреди серии;
- клиент считает ту же арифметику локально, поэтому счётчик растёт сразу,
  а ответ сервера с ним совпадает — без скачков.

Respect намеренно **не зависит от апгрейдов**: DONC растёт от прокачки,
Respect измеряет только вложенный труд. При 1000 энергии полная «обойма»
даёт 20 Respect против 1000+ DONC.

### Где отдаётся

Поле `respect` (плюс `respectProgress` и `tapsPerRespect`) входит в
игровое состояние, которое возвращают `POST /api/game/tap`,
`GET /api/game/state`, `POST /api/auth/telegram` и ответ на покупку
улучшения. В ответе тапа есть ещё `respectAwarded` — сколько начислено
этим запросом.

> Ответ на исходную формулировку задачи: эндпоинты в проекте называются
> `/api/game/tap` и `/api/game/state` — это и есть «/api/tap» и
> «/api/user/me» из постановки.

На экране игры Respect стоит рядом с DONC — отдельный счётчик со звездой
([client/src/game/GameScreen.tsx](client/src/game/GameScreen.tsx)).

## Ранги

Ранг зависит от **накопленного дохода** (`totalEarned`) и **не хранится в
базе** — вычисляется на лету функцией `resolveRank`.

Именно от накопленного, а не от текущего баланса: иначе покупка улучшения или
взнос в клан понижали бы ранг, и игрок мог потерять доступ к кланам, пожертвовав
в кассу. `totalEarned` только растёт и тратами не уменьшается. Пороги вынесены в
[server/src/config/ranks.ts](server/src/config/ranks.ts): поменяли число —
ранги пересчитались у всех сразу, без миграций и фоновых задач.

Рангов шесть, но у каждого **три звезды** — итого 18 ступеней. Так художник
рисует по-прежнему шесть персонажей, а игрок получает повышение каждые
один-три дня вместо пустых недель между рангами.


надписью и становится ключом от новой строчки в каталоге.

сразу, без перезахода.

На экране игры ранг стоит крупно под именем, ниже — полоска прогресса с
подписью вида «340 000 / 650 000 ДонКоинов до Приближённый ★★★» и рядом звёзд

Названия рангов в интерфейсе русские, в подписи прогресса — латиницей
(`code` в конфиге), как в постановке задачи.

Доля на полоске считается от порога следующего ранга — так же, как читается
подпись. Пока сервер не подтвердил повышение, показ ограничен порогом, иначе
на секунду мелькало бы «500 005 / 500 000».

## Кланы

Открываются с ранга «Солдат ★» (1 950 000 DONC). Порог не зашит в код кланов —
берётся из флага `canJoinClan` в [config/ranks.ts](server/src/config/ranks.ts),
поэтому меняется вместе с балансом рангов.

### Правила

- один клан на игрока; вступить и создать можно только с нужного ранга;
- название 3–24 символа, уникально **без учёта регистра** — «Корлеоне» и
  «корлеоне» это один клан. Гарантию даёт функциональный индекс
  `lower(name)` в базе, а не только проверка в коде, поэтому и гонка двух
  одновременных созданий не пройдёт;
- взносы уходят в кассу семьи и учитываются как личный вклад участника;
  списание идёт с условием «денег хватает», уйти в минус нельзя;
- владелец не может выйти, пока в клане есть другие; оставшись один — он
  распускает клан вместе с казной.

### Эндпоинты

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/clans` | свой клан, список кланов, требуемый ранг |
| `POST` | `/api/clans` | создать клан `{ name }` |
| `POST` | `/api/clans/:id/join` | вступить |
| `POST` | `/api/clans/leave` | выйти или распустить |
| `POST` | `/api/clans/donate` | внести в кассу `{ amount }` |

Ошибки правил приходят с кодом: `RANK_TOO_LOW`, `ALREADY_IN_CLAN`,
`NOT_IN_CLAN`, `NAME_TAKEN`, `BAD_NAME`, `OWNER_MUST_DISBAND`,
`NOT_ENOUGH_COINS`, `BAD_AMOUNT`. Ответ на взнос содержит новое игровое
состояние, поэтому баланс на других вкладках обновляется сразу.

На клиенте — вкладка **Клан**
([client/src/clans/ClanScreen.tsx](client/src/clans/ClanScreen.tsx)): своя
карточка с кассой и списком участников по вкладу либо список кланов с
кнопкой «Вступить».

## Проверка без настоящей базы

Юнит-тесты (`npm test -w server`) проверяют формулы. Они не поймают ни ошибку
в написанной руками миграции, ни расхождение между колонкой в базе и полем,
которого ждёт код, ни маршрут, отвечающий не тем, что разбирает клиент. Это
видно только при запуске.

Запускать было негде: миграции пишутся руками (`prisma migrate dev` требует
живого подключения), докера нет, Postgres локально нет, строка подключения
к Neon одна и та же для прода. Поэтому проверка поднимает Postgres **прямо
в процессе** — PGlite, это Postgres, собранный в WASM.

```bash
npm install --no-save --ignore-scripts @electric-sql/pglite @electric-sql/pglite-socket
npm run verify
```

PGlite намеренно не входит в зависимости проекта: в сборке сайта он не
участвует, а весит заметно. Ставится разово, флагом `--no-save`.

Что происходит за одну команду:

1. поднимается Postgres в памяти и выставляется в TCP-порт;
2. накатываются миграции — тот же SQL, что применит `migrate deploy` на
   проде (сам движок миграций Prisma с сокетом PGlite не договаривается,
   поэтому SQL выполняется напрямую), и сразу же сверяется со схемой;
3. отрабатывает сид;
4. стартует настоящий сервер;
5. по нему проходит путь живого игрока — 85 проверок.

Проверяется то, что ломается молча: подпись initData (и что подделанная не
проходит), списание энергии по 10 единиц за тап, множитель «Разгона»,
заряды бустеров и их суточный лимит, неизменность заданий в течение дня,
ежедневный бонус и защита от повторной выдачи, перебор шифра, лимит подписок
у рекламной кампании, недоступность админки постороннему, реферальные
начисления обеим сторонам.

База живёт в памяти, поэтому каждый запуск начинается с чистой — и миграции
всегда прогоняются с нуля.

Отдельно, если нужно проверить только миграции (быстрее и без сервера):

```bash
npm run check:migrations -w server
```

Скрипт применяет их по порядку на пустой базе и сверяет получившиеся таблицы
со схемой Prisma: ловит и битый SQL, и поле, которое появилось в схеме, но
не доехало до миграции.

## Фоны: обстановка и первый сток монет

Персонажи рангов — намеренно разные люди, поэтому «стал богаче» по самой
фигуре не читается. Это берёт на себя фон за спиной: подворотня, закусочная,
бильярдная, ресторан, кабинет, мраморный зал. Повышение видно раньше, чем
игрок прочитает надпись.

Вторая причина важнее косметики. До сих пор **в игре не было ни одной траты,
которая не возвращает деньги**: улучшения, бизнесы и перки увеличивают доход,
поэтому чем дальше, тем быстрее растёт баланс и тем меньше находится, на что
его деть. Фон — первый настоящий сток: монеты исчезают насовсем, доход не
меняется, зато остаётся то, что видно каждый заход.

| Фон | Бесплатно с ранга | Порог ранга | Цена до этого |
| --- | --- | --- | --- |
| Подворотня | Аутсайдер ★ | 0 | — |
| Закусочная | Приближённый ★ | 78 000 | 8 000 |
| Бильярдная | Солдат ★ | 2 400 000 | 250 000 |
| Ресторан | Капо ★ | 72 000 000 | 7 000 000 |
| Кабинет | Консильери ★ | 2 200 000 000 | 220 000 000 |
| Мраморный зал | Дон ★ | 66 000 000 000 | 6 500 000 000 |

### Почему цена — десятая доля порога, а не сколько захочется

**Потолок жёсткий.** Баланс никогда не превышает пожизненный заработок
(баланс = заработок минус траты), а ранг считается от заработка. Значит цена
выше порога недостижима по построению: чтобы её набрать, надо заработать
больше порога — а тогда фон уже выдан даром.

Первая версия каталога была именно такой: цены стояли в полтора порога, и все
пять платных фонов оказались мёртвым грузом. На глаз это незаметно — числа
выглядят правдоподобно, покупка просто никогда не случается. Теперь
[тест](server/src/config/backdrops.test.ts) не даёт поставить цену выше
порога, и он же следит за другой крайностью: дешевле десятой доли порога сток
перестаёт быть стоком.

**Но и подходить к пределу незачем.** Ранговый фон игрок всё равно получит
через день-другой, когда возьмёт ранг. Значит покупка — это плата за «увидеть
раньше», а не за «получить». За такое не отдают день дохода: разумный игрок
подождёт, и витрина будет стоять пустой. Первая попытка ставила четверть
порога — купить стало возможно, но незачем.

Десятая доля — цена импульса, а не расчёта. Тест держит вилку: дороже
пятой доли покупка теряет смысл, дешевле двадцатой выглядит случайной.

В витрине рядом с ценой прямо написано, на каком ранге фон достанется даром —
пусть покупает тот, кто не хочет ждать, а не тот, кто не понял.

### Настоящий сток — это другое

Ранговые фоны стоком не являются и стать им не могут: сток — это то, что
нельзя получить, просто переждав. Для него нужны фоны, которые не даёт ни
один ранг: праздничные, сезонные, за приглашённых. Каталог такие уже
поддерживает — `freeFromStep: null`, цена любая, — но картинок под них пока
нет. Каждая такая картинка это одна строка в конфиге и один файл.

Каталог — [config/backdrops.ts](server/src/config/backdrops.ts), витрина
живёт во вкладке «Дело» разделом «Вид». Какой фон показывать, решает сервер
и отдаёт готовым путём в состоянии игры: клиенту незачем знать каталог и тем
более проверять права.

Картинок может ещё не быть — тогда экран выглядит как раньше, а в витрине
остаётся тёмная плашка вместо превью. Отсутствие фона должно читаться как
решение, а не как поломка. Как их готовить — [scripts/build-sprite.md](scripts/build-sprite.md).

## Проверка готовности к запуску

Половина настроек этой игры живёт вне кода: токен бота, права бота в чужих
каналах, адрес Mini App, список владельцев, секрет планировщика. Каждая
ломается молча и по-своему — проверка подписки отвечает «попробуйте позже»,
сводка владельца отдаёт 404, реферальные ссылки ведут не туда. Разбирать это
по симптомам долго, поэтому есть список:

```bash
npm run doctor
```

Команда берёт те же переменные окружения, что и боевой сервер, — значит
может проверять прод:

```bash
DATABASE_URL="..." TELEGRAM_BOT_TOKEN="..." npm run doctor
```

Что смотрит:

- база отвечает, каталог бизнесов не пуст;
- все миграции из репозитория применены (иначе прод работает на старой схеме);
- токен бота принят Telegram, и чей это бот;
- **бот — администратор в каждом канале идущих кампаний.** Это самая частая
  поломка: кампания заведена, игрок подписался, а награду получить нельзя,
  потому что бот не может спросить у Telegram состав участников;
- владельцы указаны, иначе сводку не откроет никто;
- секрет планировщика задан, иначе напоминания и итоги войн не работают.

Про `VITE_MINI_APP_LINK` команда только напоминает: переменная попадает в
бандл на сборке, и с сервера её не видно.

### Локальная база для разработки

Если Neon под рукой нет, Postgres можно поднять прямо в процессе (PGlite —
Postgres, собранный в WASM):

```bash
npm install --no-save --ignore-scripts @electric-sql/pglite @electric-sql/pglite-socket
node server/scripts/local-db.mjs
```

Миграции накатываются при старте, база живёт в памяти и обнуляется при
перезапуске. Дальше обычная работа с `DATABASE_URL` на неё:

```bash
DATABASE_URL="postgresql://postgres:postgres@127.0.0.1:55432/postgres" npm run db:seed -w server
```

Одна тонкость: скрипты, которые ходят в эту базу, должны закрывать
соединение (`prisma.$disconnect()`) и выходить через `process.exitCode`, а не
`process.exit()`. Принудительный выход обрывает сокет, не дав ему закрыться, и
следующая команда уже не подключится.

## Защита и эксплуатация

### Сессионные токены

Раньше каждый игровой запрос нёс сырые `initData`, а они живут сутки — у
приложения, открытого дольше, всё начинало отдавать 401 без возможности
обновиться.

Теперь `POST /api/auth/telegram` возвращает подписанный сессионный токен
([server/src/lib/session.ts](server/src/lib/session.ts)), и запросы идут с
`Authorization: Bearer <токен>`. Токен живёт неделю, хранится только у
клиента и содержит лишь `telegramId` и срок — на сервере ничего хранить не
нужно, что важно для serverless.

Подпись — HMAC-SHA256 ключом, производным от токена бота (или от
`SESSION_SECRET`, если задать его в переменных окружения). Старая схема
`Authorization: tma <initData>` продолжает приниматься, чтобы уже открытые
вкладки не сломались при выкатке.

Клиент при 401 автоматически проходит вход заново — накопленные тапы при этом
не теряются.

### Ограничение частоты

[server/src/middleware/rateLimit.ts](server/src/middleware/rateLimit.ts) —
«дырявое ведро» на игрока:

| Лимит | Маршруты | В среднем | Всплеск |
| --- | --- | --- | --- |
| `game` | `/api/game/*` | 4 запроса/с | 20 |
| `write` | улучшения, кланы, рефералы | 1 запрос/с | 10 |
| `auth` | вход | 0.5 запроса/с | 5 |

Энергия и так ограничивает заработок — лимиты нужны, чтобы один клиент не
сжёг лимиты Neon и Vercel тысячами запросов. Клиент шлёт тапы пачками раз в
700 мс (1.4 запроса/с), так что в обычную игру лимит не упирается.

Проверено залпом: из 60 параллельных запросов проходят 20, остальные получают
`429` с заголовком `Retry-After`; через секунды ведро наполняется.

**Ограничение:** счётчик живёт в памяти процесса, а на Vercel инстансов
несколько — фактический потолок кратно выше заявленного. Против одного
зарвавшегося клиента этого достаточно; для жёстких лимитов нужен общий
счётчик (Upstash Redis) — отдельная задача.

### Пул подключений

На Vercel каждый инстанс держит свой пул, поэтому там он ограничен тремя
соединениями с коротким временем простоя, локально — десятью
([server/src/lib/prisma.ts](server/src/lib/prisma.ts)). Иначе десяток тёплых
инстансов упрётся в лимит соединений Neon.

### Отдельная база для разработки

Сейчас `npm run dev` и `npm run dev:mock` пишут в **боевую** базу: тестовые
игроки, накрученные балансы и мусорные кланы попадают туда же, где реальные
данные. Лечится за пару минут:

1. Neon → проект → **Branches** → **New branch** → назвать `dev`
   (ветка создаётся мгновенно и содержит копию схемы и данных);
2. на ветке нажать **Connect**, включить пулинг и скопировать строку;
3. вставить её в `server/.env` как `DATABASE_URL`;
4. боевую строку оставить только в переменных окружения Vercel.

После этого локальные эксперименты идут в свою копию, а прод остаётся чистым.
Код менять не нужно.

## Возвращаемость: оффлайн-доход и ежедневный бонус

Настройки в [server/src/config/rewards.ts](server/src/config/rewards.ts).

### Оффлайн-доход

Пока игрока нет, «семья работает»: монеты капают со скоростью **20% от
активного дохода**, но не дольше **3 часов** — чтобы был смысл заходить чаще.

```
монет в час = coinsPerTap × energyPerSecond × 3600 × 0.2
```

Формула намеренно завязана на скорость восстановления энергии: ветка «Связи»
до этого была почти бесполезна при игре сессиями — энергия всё равно упиралась
в потолок. Теперь каждый её уровень напрямую увеличивает оффлайн-доход.

Начисляется автоматически при входе, а не по кнопке: одна запись в базу вместо
двух, и деньги нельзя потерять, закрыв приложение до нажатия. `lastSeenAt`
обновляется и при входе, и при каждом тапе — иначе после долгой активной
сессии игроку начислился бы «оффлайн» за то время, что он играл.

### Ежедневный бонус

Награда привязана к текущей силе игрока, а не фиксирована — иначе к середине
игры она обесценивалась бы:

```
награда = coinsPerTap × energyMax × 0.25 × min(день серии, 7)
```

Серия растёт, если предыдущий бонус взят вчера, и сбрасывается на единицу при
пропуске. Границы суток — по UTC, чтобы не разбираться с часовыми поясами.

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/daily` | доступен ли бонус, какой день и награда |
| `POST` | `/api/daily/claim` | забрать |

Повторное получение отбивается кодом `ALREADY_CLAIMED`, причём условие по
дате стоит прямо в `UPDATE` — два одновременных запроса дают одно начисление
(проверено тестом).

Статус бонуса и оффлайн-доход приходят вместе с ответом на вход, поэтому
лишних запросов при старте нет.

## Лидерборд

Вкладка **Топ** с двумя списками: игроки по заработанному за всё время
(`totalEarned`) и кланы по кассе. Первые три места отмечены медалями, своя
строка подсвечена, а если игрок не попал в показанные 50 — его позиция
показывается отдельной строкой снизу.

`GET /api/leaderboard` возвращает оба топа и собственные позиции одним
запросом ([server/src/routes/leaderboard.ts](server/src/routes/leaderboard.ts)).

Позиция считается через `COUNT` «сколько игроков выше меня», а не нумерацией
всей таблицы — по индексу это дешевле. Под сортировку и подсчёт добавлены
индексы `User.totalEarned` и `Clan.treasury`: без них каждый запрос читал бы
таблицу целиком.

Ранжирование по `totalEarned`, а не по балансу — так игрок, вложившийся в
улучшения или кассу, не проваливается в таблице.

> В списке видны имена из Telegram и суммы. Это обычная практика для таких
> игр, но если захотите приватности — можно показывать только `username` или
> обезличенные псевдонимы.

| Размять пальцы | 500 тапов | 2 000 |

**Прогресс нигде не хранится** — он выводится из уже существующих полей:
количество тапов восстанавливается из `respect × 50 + respectProgress`
(Respect выдаётся ровно за каждые 50 тапов), покупки — из уровней улучшений,
друзья — из связи `referredById`. В базе лежит только список полученных
наград (`claimedTasks`). Поэтому прогресс невозможно рассинхронизировать с
реальностью, а новое задание добавляется без миграции.

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/tasks` | список с прогрессом |
| `POST` | `/api/tasks/:id/claim` | забрать награду |

Условие «награда ещё не получена» стоит прямо в `UPDATE`, поэтому два
одновременных запроса дают одно начисление. Невыполненное задание отбивается
кодом `NOT_DONE`.

На клиенте задания открываются кнопкой под ежедневным бонусом — панелью
поверх экрана ([client/src/tasks/TasksPanel.tsx](client/src/tasks/TasksPanel.tsx)),
чтобы не заводить шестую вкладку. Кнопка показывает, сколько наград готово к
получению.

## Бизнесы

Пассивный доход: каталог общий для всех, уровни — у каждого свои.

| Бизнес | Цена | Доход в час | Окупаемость |
| --- | --- | --- | --- |
| Пиццерия | 2 000 | 100 | 20 ч |
| Автомойка | 10 000 | 450 | 22 ч |
| Ресторан | 50 000 | 2 000 | 25 ч |
| Ночной клуб | 250 000 | 9 000 | 28 ч |
| Строительная компания | 1 200 000 | 40 000 | 30 ч |
| Закрытый клуб | 6 000 000 | 180 000 | 33 ч |
| Портовый бизнес | 30 000 000 | 800 000 | 37,5 ч |

### Логика баланса

**Между бизнесами.** Каждая следующая ступень стоит примерно в пять раз
дороже предыдущей, а доход растёт медленнее — окупаемость ползёт с 20 до
37,5 часов. Значит дешёвые бизнесы выгоднее по вложенному DONC, а дорогие
берут абсолютом. Без этого перекоса первый же доступный бизнес обесценил бы
весь остальной каталог.

Шаг в пять раз привязывает каталог к росту игрока: пиццерия по карману в
первый час, порт — уже ближе к рангу «Дон» (50 млн заработанного).

**Внутри бизнеса.** Цена уровня растёт как `baseCost × 1.15^level`, а доход
линейно — `baseIncomePerHour × level`. Каждый следующий уровень окупается на
15% дольше предыдущего: качать вглубь можно долго, но бесконечно выгодным это
не станет.

**Относительно тапов.** Весь каталог на первом уровне даёт около 1 млн в час
при вложенных 37,5 млн. Это сопоставимо с доходом от тапов у прокачанного
игрока — бизнесы примерно удваивают заработок, но не заменяют игру.

Баланс правится в [server/src/config/businesses.ts](server/src/config/businesses.ts),
оттуда же его забирает seed:

```bash
npm run db:seed
```

Скрипт обновляет записи по `slug`, поэтому запускать его можно сколько угодно
раз — дубли не появятся, а правка цен доедет до базы одним запуском.

### Начисление дохода

У бизнесов свой отсчёт времени (`businessCollectedAt`), и он **не
сбрасывается тапами** — предприятия работают и пока игрок в приложении.
Потолка накопления нет: владелец заплатил полную цену, и «сгорающий» доход
только раздражал бы.

Деньги зачисляются при входе и перед покупкой — то есть там, где запись в
базу и так происходит. На `GET` начисления нет (запись на чтение — плохая
идея), но накопленное показывается в интерфейсе.

### Эндпоинты

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/businesses` | каталог с уровнями игрока и доходом |
| `POST` | `/api/businesses/:id/buy` | купить или улучшить на уровень |

Списание и повышение уровня идут одной транзакцией с условиями «денег
хватает» и «уровень не изменился» — две одновременные покупки не уводят
баланс в минус и не дают лишний уровень (проверено тестом).

На клиенте бизнесы живут во вкладке **Дело** рядом с прокачкой — под общим
переключателем ([client/src/deal/DealScreen.tsx](client/src/deal/DealScreen.tsx)).
Шестую вкладку заводить не стали: пять и так тесно на узких экранах.

## Рекламные кампании

На них игра зарабатывает: рекламодатель покупает подписчиков, игрок получает
монеты за подписку, его клан — опыт семьи (`Clan.familyXp`).

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/favors` | идущие кампании с отметкой о выполнении |
| `POST` | `/api/favors/:id/complete` | проверить подписку и начислить награду |
| `GET` | `/api/admin/ads` | все кампании со статусом и выдачей |
| `POST` | `/api/admin/ads` | завести или обновить кампанию |
| `POST` | `/api/admin/ads/:id/stop` | снять с показа |

### Кампании заводятся из админки, а не из кода

Раньше каталог лежал в `config/favors.ts`, срок задавался номером ISO-недели,
а заливал всё seed-скрипт. То есть новый рекламодатель стоил коммита с
деплоем, а сид гасил всё, чего нет в каталоге. Продавать так нельзя.

Теперь кампания — строка в базе, которую владелец заводит прямо в панели
сводки (**⚙ → Реклама → + Кампания**). Сид рекламу не трогает вовсе.

Что задаёт владелец:

| Поле | Смысл |
| --- | --- |
| `channelChatId` | `@username` канала — по нему проверяется подписка |
| `rewardDonc` | фиксированная награда, работает нижней границей |
| `rewardHours` | награда в часах дохода игрока |
| `slots` | сколько подписок куплено, пусто — без лимита |
| `startsAt` / `endsAt` | срок размещения, пусто — бессрочно |
| `advertiser` | для отчётности, игроку не показывается |

### Почему награда в часах дохода

Фиксированная сумма, щедрая для новичка, к «Капо» перестаёт быть поводом
подписываться — то есть кампания теряет ровно тех, кто играет дольше всех.
`rewardHours` привязывает награду к часовому доходу самого игрока, а
`rewardDonc` остаётся нижней границей: у новичка час дохода — копейки.

### Лимит подписок

Рекламодатель покупает конкретное число подписок. Счётчик `completedCount`
увеличивается в той же транзакции, что и выдача награды, причём условием
`completedCount < slots` прямо в `WHERE`: между проверкой и выдачей могли
уложиться другие игроки, и без этого условия игра раздала бы больше, чем
оплачено. Когда лимит выбран, задание пропадает из списка само.

Игроку остаток показывается только под конец (меньше 100) — «осталось 4980»
читается как шум, а «осталось 12» заставляет поторопиться.

### Проверка подписки

Награда выдаётся только после подтверждения: сервер вызывает
`getChatMember` у Telegram Bot API
([lib/telegramApi.ts](server/src/lib/telegramApi.ts)). Клиент не может ни
подтвердить подписку за себя, ни обойти проверку.

**Бот должен быть администратором канала** — иначе Telegram не отдаёт состав
участников, и проверка отвечает `CHECK_UNAVAILABLE`. Это первое, что стоит
проверить, если кампания заведена, а награды не выдаются.

### Снятие с показа

Кампания снимается (`active: false`), а не удаляется: у игроков остались
отметки о выполнении, по ним считается отчёт рекламодателю, да и внешний ключ
не пустил бы DELETE.

На клиенте кампании живут во вкладке **Семья** рядом с друзьями
([client/src/favors/FavorsScreen.tsx](client/src/favors/FavorsScreen.tsx)):
заголовок «The Family needs a favor», карточки с кнопками «Перейти» и
«Проверить», у выполненных — отметка вместо кнопок. Ссылки открываются
внутри Telegram через `openTelegramLink`.


## Сводка для владельца

Закрытый раздел с метриками: `GET /api/admin/stats`
([server/src/routes/admin.ts](server/src/routes/admin.ts)). В приложении
открывается кнопкой «Сводка» в углу игрового экрана — её видят только
администраторы.

### Доступ

Задаётся переменной `ADMIN_TELEGRAM_IDS` (Telegram ID через запятую). Пустое
значение означает «никому» — лучше остаться без доступа, чем случайно открыть
статистику всем.

Посторонним раздел отвечает **404, а не 403**: незачем сообщать, что он
вообще существует.

### Что показывает

| Блок | Метрики |
| --- | --- |
| Игроки | всего, пришли за сутки и за неделю, заходили за сутки (DAU) и за неделю (WAU) |
| Удержание | доля вернувшихся на 1, 3, 7 и 30-й день после регистрации |
| По дням | заходы и новички за каждый из последних 14 дней |
| Докуда доходят | купили улучшение, купили бизнес, забрали бонус, вступили в клан, пришли по реферальной ссылке, выполнили поручение — с долей от всех игроков |
| Экономика | DONC на руках, заработано за всё время, богатейший игрок, число кланов |
| Топ | пять игроков по заработку |

### Удержание

DAU и WAU говорят, сколько людей в игре сегодня. Они не отвечают на главный
вопрос: возвращаются ли те, кто пришёл. Игра с удержанием второго дня ниже
трети не лечится рекламой — в неё просто доливают воду.

Считается не «заходил ли хоть раз после регистрации», а **заходил ли именно
на N-й день**. Первое растёт само собой со временем и выглядит прилично,
ничего при этом не измеряя. В знаменателе только те, кто успел дожить до
нужного дня, иначе вчерашние новички занижали бы недельное удержание до нуля.
Пока считать не на ком, показывается прочерк, а не ноль — это разные вещи.

Для этого понадобилась таблица `DailyActive`: одна строка на игрока в сутки.
По `lastSeenAt` удержание не посчитать — там только последний визит, и был
ли человек в игре на третий день, оно не помнит.

Запись идёт не чаще раза в сутки на игрока: при входе сравнивается день
прошлого визита с сегодняшним, и если он тот же, до базы дело не доходит.
Ошибка записи глотается — это статистика, и она не должна мешать входу.

«Вернулись на следующий день» считается сравнением `lastSeenAt` с
`createdAt + 24 часа` — то есть заходил ли человек хотя бы через сутки после
регистрации. Это единственная метрика, которой нужен сырой SQL: сравнение
двух колонок обычным `where` в Prisma не выражается.

Полноценного журнала событий нет — всё, кроме заходов по дням, считается из
текущего состояния игроков. `DailyActive` завели именно потому, что удержание
из состояния не выводится ни при каких ухищрениях.

## Напоминания от бота

Всё остальное в игре окупается, только если человек её откроет. Напоминания —
единственная механика, которая возвращает игрока без его участия.

### Что и когда отправляется

За один прогон игрок получает **одно** сообщение — самое ценное из возможных:

| Повод | Условие | Почему первым |
| --- | --- | --- |
| Сгорает серия | бонус за сегодня не забран, серия уже идёт, после 17:00 МСК | потеря мотивирует сильнее выгоды |
| Бизнесы накопили | скопилось от 1 000 DONC | конкретная выгода, которую можно забрать |
| Энергия полная | запас восстановился до максимума | обычное напоминание |

Если ни один повод не подошёл — не пишем вовсе.

### Ограничители

Правила в [server/src/config/notifications.ts](server/src/config/notifications.ts):

- игрок не заходил минимум **6 часов**;
- прошлое сообщение было не раньше чем **20 часов назад**;
- **тихие часы** 22:00–09:00 МСК (часовой пояс Telegram не сообщает, берём
  основную аудиторию);
- не больше 30 сообщений за прогон, с паузой между отправками.

Размер пакета упирается не в Telegram, а в лимит времени serverless-функции.
Всё общее для рассылки (каталог бизнесов, бизнесы игроков, кланы) грузится
**тремя запросами на весь пакет**: раньше на каждого адресата уходило три
отдельных запроса и 760 мс, из-за чего прогон на сотне игроков занял бы
102 секунды и не уложился бы в лимит. Сейчас подготовка одного сообщения
стоит около 3 мс.

Игру, которая пишет слишком часто, не выключают — её блокируют, и вернуть
человека уже нельзя. Поэтому ограничители жёсткие, а **выключатель есть у
каждого**: шестерёнка в углу игрового экрана.

Если Telegram отвечает, что бот заблокирован, игрок помечается
(`notificationsBlocked`) и больше не тревожится. Сбой сети или неверный токен
такой отметки **не** ставят — проверено тестом.

### Запуск по расписанию

Эндпоинт `/api/cron/notify` защищён секретом `CRON_SECRET` и принимает оба
способа авторизации: `x-cron-secret` для внешних планировщиков и
`Authorization: Bearer`, который Vercel Cron подставляет сам. Без секрета —
404.

Планировщиков два:

1. **GitHub Actions** ([.github/workflows/notify.yml](.github/workflows/notify.yml)) —
   основной, каждые 3 часа. Нужен секрет репозитория `CRON_SECRET`.
2. **Vercel Cron** (в [vercel.json](vercel.json)) — раз в сутки в 18:00 МСК,
   как подстраховка. На бесплатном тарифе чаще нельзя, а энергия
   восстанавливается за часы — поэтому одного Vercel мало.

### Что настроить

| Где | Переменная | Значение |
| --- | --- | --- |
| Vercel → Environment Variables | `CRON_SECRET` | случайная строка |
| GitHub → Settings → Secrets → Actions | `CRON_SECRET` | то же значение |

**Значения должны совпадать.** Без секрета в репозитории расписания просто
не работают: напоминания не уходят, войны не закрываются. Диагностика по
коду ответа:

| Код | Что значит |
| --- | --- |
| 200 | всё в порядке |
| 404 | секрет не совпал с тем, что задан в Vercel |
| 503 | в Vercel переменная `CRON_SECRET` не задана вовсе |

Эндпоинт отвечает 404, а не 403, намеренно: посторонним незачем знать, что
такой раздел существует. Из-за этого же молчаливое падение планировщика
ничего не объясняло, поэтому workflow разбирает коды и пишет причину в лог.


## Дневная петля: бустеры, задания дня и шифр

Ранги и бизнесы отвечают на вопрос «зачем играть месяц». Этот раздел — про
«зачем открыть игру сегодня и ещё раз вечером».

### Бустеры

Два бустера, по три бесплатных заряда в сутки
([config/boosters.ts](server/src/config/boosters.ts)):

| Бустер | Что делает |
| --- | --- |
| Полная обойма | мгновенно заполняет обойму |
| Разгон | ×5 за тап на 20 секунд |

Счётчики не сбрасываются фоновой задачей — они «протухают» вместе с полем
`boostDay` и обнуляются при первой же трате в новые сутки. Отдельный
планировщик ради этого не нужен.

Множитель «Разгона» применяется прямо в атомарном UPDATE тапа: сравнение
`rushEndsAt > now()` идёт по часам базы, поэтому подкрутить время на клиенте
бесполезно.

Три заряда — это три причины зайти. Это же очевидная точка монетизации:
докупать заряды за Telegram Stars можно, ничего не меняя в балансе.

### Задания дня

Три задания, новые каждые сутки, плюс сундук за все три
([config/quests.ts](server/src/config/quests.ts)). Выбор детерминированный —
хеш от пары (игрок, день): у разных людей задания разные, а пересчёт всегда
даёт тот же результат.

Прогресс нигде не копится по событиям. Он считается как разница между
текущими показателями игрока и слепком, снятым при первой за сутки загрузке
(`DailyQuestDay.base*`). Иначе каждый тап пришлось бы писать ещё и в счётчик
заданий, а тап — это один UPDATE, и он должен таким остаться.

Награды привязаны к силе игрока (доля часа активного дохода), поэтому не
обесцениваются к «Капо».

### Шифр дня

Код прячется в канале, вводится в игре, даёт шесть часов дохода
([config/cipher.ts](server/src/config/cipher.ts)). Смысл не в награде, а в
том, что игра начинает кормить канал: за кодом нужно идти туда, где живёт
аудитория. Это же делает канал ценным для рекламодателей — то есть шифр
окупается снаружи игры, а не внутри.

Шифр задаётся в сводке владельца (шестерёнка → панель статистики), раздел
«Шифр дня»: день, код, подсказка. Там же видно, сколько человек разгадало
вчерашний, — это прямая мера того, доходит ли аудитория до канала.

Готовить удобнее на завтра: код должен появиться в канале раньше, чем игроки
пойдут его искать.

То же самое запросом, если удобнее так:

```
POST /api/admin/cipher
{ "code": "ОМЕРТА", "hint": "Ищите в закрепе", "day": 1 }
```

`day` — смещение в сутках от сегодняшних, 0 — сегодня.

### Почему попыток десять

Перебор ограничен `CIPHER_ATTEMPTS_PER_DAY` попытками в сутки, и попытка
списывается **до** сравнения кода — иначе неверный ввод не стоит ничего.

Без лимита смысл шифра пропадает целиком: даже трёхбуквенный код подбирается
скриптом за минуты, награда уходит тем, кто в канал не заходил, а
рекламодателю нечего показать. Счётчик протухает вместе с `cipherDay` — тем
же приёмом, что и заряды бустеров, без фоновой задачи.

## Уход на покой

Дойдя до «Дона ★★★», игрок упирается в стену: качать нечего, ранга выше нет,
и через день-другой он уходит навсегда. Уход на покой
([config/retirement.ts](server/src/config/retirement.ts)) обнуляет нажитое и
возвращает в начало, но даёт **+10% к доходу навсегда** за каждый круг — то
есть второй круг короче первого, третий короче второго.

| Обнуляется | Остаётся |
| --- | --- |
| баланс, накопленный заработок | Respect и купленные за него перки |
| уровни улучшений | клан, друзья, выполненные задания |
| бизнесы | пожизненный заработок и титул |

Прибавка упирается в потолок на десятом круге: без него экономика ломается.

### Почему появился пожизненный заработок

Уход обнуляет `totalEarned`, а по нему строился лидерборд — то есть прошедший
игру до конца улетал на дно ровно за то, что прошёл её до конца. Поэтому
рядом появилось поле `lifetimeEarned`: растёт везде, где растёт накопленный,
но уходом не обнуляется. Лидерборд считает по нему.

### Почему действие живёт в настройках

Оно необратимое и требует второго нажатия. На экране, где играют, такой
кнопке не место.

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/retirement` | сколько кругов пройдено и можно ли уйти |
| `POST` | `/api/retirement` | уйти на покой |

Обнуление идёт одной транзакцией под условием «заработка хватает и счётчик
кругов не менялся»: иначе два одновременных запроса засчитали бы два круга
за один проход игры.

## Влияние: траты Respect и сила семьи

До этого Respect, касса и опыт семьи только копились и ни на что не
влияли. Теперь у всех троих есть последствия.

### Траты Respect

Вкладка **Дело → Влияние**. Три ветки по 60 уровней, +2% за уровень, цена
растёт в 1.25 раза ([server/src/config/perks.ts](server/src/config/perks.ts)):

| Улучшение | Что усиливает | Старт |
| --- | --- | --- |
| Слава на улице | монеты за тап | ★15 |
| Деловая хватка | доход бизнесов | ★18 |
| Связи в семье | доход, пока игрока нет | ★12 |

Было «три ветки по 10 уровней, +5%»: ветка выдыхалась за вечер и упиралась
в +50% навсегда, после чего Respect копился впустую. Теперь прибавка меньше,
зато уровней столько, что упереться в потолок нельзя — ограничителем работает
цена, а не число.

Сам `respect` при покупке **не уменьшается** — он отражает вложенный труд и
служит для лидерборда. Расход учитывается отдельным полем `respectSpent`, а
тратится «свободный остаток» = `respect - respectSpent`.

Прибавка за тап применяется прямо в атомарном UPDATE тапа
(целочисленная арифметика в SQL), прибавки к бизнесам и оффлайну — в TS,
где уже загружен клан.

### Сила семьи

Уровень клана считается не только по деньгам:

```
сила = касса + опыт за поручения × 5 000
```

Пороги: 100 тыс, 500 тыс, 2 млн, 10 млн, 50 млн — то есть 5 уровней. Каждый
даёт **всем участникам** +3% к пассивному доходу (бизнесы и оффлайн).

Опыт за поручения весит дорого намеренно: иначе клан прокачивался бы только
взносами богатых, а вклад обычного игрока ничего не значил бы. Теперь взнос в
касса — вложение, а не пожертвование.

### Пороги рангов понижены

Кланы показывали 0% в воронке: порог «Солдата» был 150 000, а второй по
богатству игрок стоял на 77 000. Теперь «Приближённый» — 15 000, «Солдат» —
50 000. Остальные ранги не тронуты.

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/perks` | ветки влияния и свободный Respect |
| `POST` | `/api/perks/:id/buy` | купить уровень за Respect |

## Персонажи рангов

Вместо золотой монеты игрок тапает по чиби-персонажу своего ранга
([client/src/game/TapCoin.tsx](client/src/game/TapCoin.tsx)). Нарисованы четыре:
«Аутсайдер», «Приближённый», «Солдат» и «Капо». На рангах, для которых
персонажа ещё нет, показывается монета — код падает на неё сам, одной
проверкой.

Все фигуры одного роста (170 пикселей) и стоят на одной линии (нижний край на
строке 188), иначе повышение выглядело бы не как рост, а как подмена.

Персонаж **двигается только пока по нему тапают**: анимация включается на
тап и выключается через 600 мс после последнего. В покое он стоит на первом
кадре.

Технически это лента из 8 кадров (`client/public/don-outsider.webp`,
142 КБ) и CSS-анимация `steps(8)` по `background-position`. Исходное видео
весило 3,9 МБ — в Mini App его тащить нельзя, оно грузилось бы каждую
сессию. Фон исходника вырезан по цвету, масштабирование без сглаживания,
чтобы пиксель-арт не замылился.

Как пересобрать ленту — [scripts/build-sprite.md](scripts/build-sprite.md).
